## Issue Classification

### Category A: Prompt-fixable (change instructions, get better output)

#### A1. `source` type underused — concept-0026 is `other`

《琵琶行》and《关雎》are cited literary works. The prompt lists `source` as a
preferred type but doesn't define when to use it. The model chose `other`.

**Fix**: Add a one-line definition in the type vocabulary section:
> `source`: cited or referenced text, letter, document, poem, or work.

Also add an anti-example:
> WRONG: `concept_type: "other"` for 《琵琶行》(a cited poem)
> RIGHT: `concept_type: "source"` for 《琵琶行》

#### A2. Supernatural entities typed as `person`

concept-0267 (神, "神仙或神灵") has type=person, no canonical_name. Should
be `term` or `other` — it's a spiritual concept, not an individual.

**Fix**: Add to the person type definition:
> `person`: named or referenced individual human. Do not use for deities,
> spirits, or supernatural beings unless they are named characters in the
> narrative.

#### A3. Facet verbosity

Prompt says "2-5 tags" but avg is 3.3, max 17, and 11 concepts have >5.
The model generates fine-grained role tags (spouse, author, husband, mourner,
artist, traveler, male, protagonist...) instead of 2-5 abstraction levels.

**Fix**: Tighten the facet instruction:
> Provide EXACTLY 2-5 facets. Fewer is better. Prefer 2-3 well-chosen
> abstraction levels over many role-tags.

#### A4. `other` type for animals/plants — missing `object` guidance

concept-0106 (螳螂), 0107 (蝉), 0108 (蝶), 0117 (扁豆), 0118 (藤本香草) are
all typed `other`. These are clearly `object` (physical things with narrative
significance). The model isn't using `object` for animals/plants.

**Fix**: Add to the object type definition in prompt:
> `object`: physical thing with narrative significance — includes animals,
> plants, artifacts, buildings, and natural features.

#### A5. Theme sets concentrate editorial commentary — extraction guidance too limiting

5 theme_sets across 3 units, and all but group-0007/0009 are editorial
"点评" (modern commentary/analysis). The extractor has no good type for
commentary content, so it defaults to `theme_set`. Group-0007 (省俭原则)
is legitimate — it's the author's own method examples. Group-0009 (作者自述)
is narrative background, arguably should be a `theme_set` or absorbed into
the main timeline.

The narrow item types (11 preferred) may be too restrictive — the extractor
lumps reflective/commentary content into `theme_set`.

**Fix**: Consider adding `reflection` or `commentary` as an item type for
editorial/analytical content, or broadening the item vocabulary slightly.
Alternatively, accept that `theme_set` is the right group type for these
and ensure the prompt distinguishes author reflection from modern editorial
commentary.

### Category B: Pipeline/merge-fixable (change code, not prompts)

#### B1. Cross-unit resolution missed obvious duplicates

**concept-0031 (沈三白) vs concept-0001 (沈复)**:
- Same person. 沈复, 号三白.
- concept-0031 aliases include '沈复'; concept-0001 aliases include '三白'.
- Both type=person, both have canonical names.
- The resolver should have proposed `link`.

**concept-0032 (芸娘) vs concept-0002 (芸娘)**:
- Same surface, same canonical_name, same type.
- concept-0032 has empty aliases but concept-0002 has ['芸娘', '陈淑珍', ...].
- Trivial deterministic match — same surface + same type should be auto-linked.

**Root cause**: These went through cross-unit resolution (they appear in
unit-0003/0004 against registry from unit-0002). The candidate_map should
have surfaced concept-0001 as a deterministic candidate for concept-0031
(via alias overlap). Either:
- The candidate_map didn't include concept-0001 for concept-0031
- The resolver LLM saw the candidate but chose `new_concept` instead of `link`
- The resolver failed to call `get_concept` to verify

**Fix**: 
- Add a deterministic pre-check: if canonical_name matches or surface
  matches exactly AND type is compatible → auto-link (no LLM needed).
- Log candidate_map misses for post-hoc debugging.
- Add to resolution prompt: "If unit concept shares an alias with a registry
  concept, that is a strong identity signal — call get_concept to verify."

#### B2. Temporal sequences not merged into timelines

Group-0010 through group-0016 (7 temporal_sequences, unit-0004) form a
continuous narrative: 芸娘 conflict → death → aftermath. Group-0001
(timeline, 56 items, unit-0002) already covers the love story arc including
item-0045 ("后来憨园被有力者夺去，计划未成。芸娘竟因此事而死") — this is
exactly where group-0013's content belongs.

The group resolution pass should have proposed `continue` on group-0001 for
these temporal sequences, or at minimum `cross_group_edge` with `part_of`.

**Root cause**: Group resolution may not be seeing group-0001 as a candidate
for group-0013 because:
- concept_refs overlap may be insufficient (group-0001 has 47 concepts,
  group-0013 has 22 — but the key connectors 芸娘/沈复 should be in both)
- The resolver defaults to `new_thread` when uncertain
- No explicit instruction to prefer `continue` on existing timelines for
  new temporal sequences with the same key entities

**Fix**:
- In group resolution prompt: "When a new temporal_sequence shares key
  person/place concepts with an existing timeline, prefer `continue` on
  the timeline over `new_thread`."
- Add deterministic pre-check: if a temporal_sequence's concept_refs are
  a subset of a timeline's concept_refs → surface as high-priority
  candidate for continue.

#### B3. concept-0235 (憨) likely a hallucinated split from concept-0042 (憨园)

concept-0235: surface=憨, summary="芸娘梦中呼喊的人，可能与阿双有关或另一人物"
concept-0042: surface=憨园, summary="温冷香之女..."

The extractor heard "憨" in a dream scene and created a new person concept
instead of recognizing it as a reference to 憨园.

**Fix**: This is primarily an extraction issue (the extractor should
recognize 憨 as short for 憨园), but the merge layer should catch it:
- Single-character surfaces that are prefixes of existing concept surfaces
  with matching type → flag as high-probability merge candidate.
- Add to resolution prompt: "Single-character names may be abbreviations of
  known multi-character names — call get_concept for the longer form."

### Category C: LLM limitations (mitigation-only, no guaranteed fix)

#### C1. Some `other` type usage is reasonable

concept-0269 (家庭矛盾) typed `other` — it's an abstract situation/conflict,
not cleanly any preferred type. The model made a defensible choice.

#### C2. Facet quality varies

Some facets are excellent (concept-0002: person, spouse, recurring_entity,
writer, designer, organizer...). Others are generic. The model's facet
generation is a function of its world knowledge, not prompt engineering.

#### C3. `technique` vs `method` distinction

The prompt lists both `technique` (preferred item type) and `method`
(preferred concept type). For novels/essays where techniques ARE methods,
the distinction is blurry. The model sometimes picks `technique` as a
concept type (2 non-standard uses) because it can't distinguish the two.

### Category D: Source block ref issues (HTML/frontend)

#### D1. Click on concept-0235 and concept-0267 doesn't jump to source block

Both have valid source_block_refs (block-000482, block-000551 respectively).
The issue is likely in the HTML rendering — either:
- The source block anchor IDs don't match the ref format
- The block isn't included in the rendered unit text
- The click handler targets the wrong element

This needs frontend debugging, not prompt/pipeline changes.

## Design implications for Phase 2c

The type definition problem (A1, A2, A4 all need 1-line definitions) is a
direct argument for Phase 2c's `TypeVocabulary.definitions` dict. Currently
adding a type definition requires editing prompt prose. With Phase 2c, it
requires adding one entry to a Python dict.

The duplicate merge problem (B1) suggests we need a deterministic pre-filter
that auto-links exact surface + type matches before the LLM sees them. This
is not a prompt fix — it's a `registry_delta.py` change.
