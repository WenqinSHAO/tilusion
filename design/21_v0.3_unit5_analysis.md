## CRITICAL: Merge corruption

### concept-0001 (沈复 → 先生)

The registry concept for 沈复 (the author/narrator) was corrupted by merging
in a unit-0005 concept for "先生" (a generic teacher/elder).

| Field | Before unit-0005 | After unit-0005 |
|-------|-----------------|-----------------|
| surface | 沈复 | **先生** |
| canonical_name | 沈复 | **先生** |
| summary includes | 叙述者，沈复... | + "作者的老师或长辈，带领作者春游扫墓" |

The unit-0005 concept "先生" (a teacher figure) was incorrectly linked to
concept-0001. After merge, the surface and canonical_name were overwritten.
The aliases still contain 沈复's names, but the primary identity fields now
point to a DIFFERENT person.

### concept-0002 (芸娘 → 作者/沈复)

The registry concept for 芸娘 (the wife) was corrupted by merging in TWO
unit-0005 concepts: one for "作者/沈复" (the author) and one for the wife.

| Field | Before unit-0005 | After unit-0005 |
|-------|-----------------|-----------------|
| surface | 芸娘 | **作者/沈复** |
| canonical_name | 芸娘 | **作者/沈复** |
| aliases | 芸娘, 陈淑珍, 芸... | + 沈复, 三白, 余 |
| summary | wife entries | + "作者本人，游记叙述者" |

The aliases now mix two different people. This is a catastrophic merge —
芸娘 (wife) and 沈复 (author) are distinct people.

### concept-0031 (沈三白) still not merged

沈三白 is 沈复's 号 (courtesy name). Still exists as a separate concept
with aliases ['沈复', '沈三白']. Should have been merged into concept-0001
but wasn't — while the unrelated "先生" WAS merged in.

### Root cause

The cross-unit concept resolution LLM proposes `link` between unit concepts
and registry concepts. When the LLM incorrectly links distinct entities,
the deterministic merge silently applies the link — there is no hard
identity guard. Concretely:

1. Unit-0005 concept "先生" (teacher) was linked to registry concept-0001
   (沈复, the author) — possibly because both appear in similar narrative
   contexts, or because the resolver was confused by shared block refs.

2. Two unit-0005 concepts (作者/沈复, 作者的妻子) were both linked to
   registry concept-0002 (芸娘) — the resolver couldn't distinguish the
   author from his wife in the summary text.

**This is the highest-priority issue.** Without identity guards, the registry
degrades with each incremental unit.

## Non-standard concept types: ITEM vocabulary bleeding into CONCEPT

11 concepts in unit-0005 use types from the item vocabulary:

| Type | Count | Example |
|------|-------|---------|
| event | 5 | 乾隆南巡, 林爽文之乱 |
| technique | 2 | 盆树剪裁, 点缀盆中花石 |
| action | 1 | 拂衣归里 |
| observation | 3 | (various) |

Registry total: 14 non-standard concept types.

**Root cause**: The LLM sees two type vocabularies (concept and item) side
by side in the same prompt. When a concept feels like a "technique" or "event,"
the LLM uses that word as the concept_type instead of the nearest concept
equivalent (`method` for technique, `other` for event).

The item vocabulary has `technique`, `event`, `action`, `observation` as
preferred types — these are the same words the LLM misuses for concepts.

## Design implication

The merge corruption (P0) is a deterministic merge safety issue. The current
pipeline has merge safety validation (`design/15` Phase 2a) but it doesn't
check whether merged concepts are actually the same person. Needed:

1. **Hard identity guard before merge**: If two concepts have the same
   `concept_type == "person"` but their canonical_names/surfaces have zero
   character overlap (e.g., "沈复" vs "先生"), block the merge and flag
   for review.

2. **Surface stability during merge**: When merging, the registry concept's
   surface and canonical_name should be preserved if they already had a
   populated value. The incoming unit concept's surface should become an
   alias, not overwrite the primary identity.

3. **Summary concatenation control**: The current `merge_concepts` appends
   summaries with `[unit-N]:` prefix. When unrelated concepts are merged,
   this creates confusing composite summaries. A merge should only happen
   after identity is confirmed.
